## 2026-07-26 16:24-17:36 — Phase 2.3: full European continent expansion + worker scaling fix

- **Type**: Two related changes in one session — additive seed data (MEDIUM risk) followed by a worker code fix discovered while verifying the deployment.
- **Scope**: All 44 remaining European countries (Western, Southern, Northern, Eastern Europe, the Balkans, and Russia), at the user's request to "move on to another continent" after Africa. 129 new publishers, individually curl-verified. Countries: 59 → 103.
- **Thin coverage, documented honestly**: Luxembourg (1 feed), Ukraine (2 — most outlets Cloudflare-blocked), Belarus (1 — only the state news agency BELTA worked, all independent outlets blocked), Montenegro (2).
- **Recovery point**: `2026-07-26_16-28-49_before-add-44-european-countries-and-the` (full DB dump, 3.7MB) — first attempt was PARTIAL (no Bastion tunnel active), re-ran after establishing one for a complete snapshot before deploying.
- **Real bug found and fixed, in three iterations**: after seeding + deploying, a manual worker poll job hit the CronJob's `activeDeadlineSeconds` (240s) and got killed before finishing — feed count had grown from 48 (Phase 2 Stage 1) to 326 (post-Europe), a ~7x increase the original sequential one-feed-at-a-time polling design never accounted for.
  1. First fix attempt: chunked feeds into lockstep batches of 20 via `Promise.all` per chunk. **Still failed** — a lockstep batch pays its slowest straggler's full cost (up to the 15s per-feed timeout) on *every* chunk, so 17 chunks × up to 15s ≈ still blew the deadline. Verified this directly rather than assuming the first fix worked.
  2. Second fix: replaced with a real worker-pool pattern (fixed number of workers pulling the next feed off a shared queue as it finishes, not barrier-synchronized batches). **Still failed**, and only marginally faster — pointed at a different bottleneck.
  3. Found the actual bottleneck: `pollFeed` awaited one `INSERT` per article, and several European feeds (La Repubblica, Lenta.ru, Vísir, etc.) carry 50-200+ items each — serialized round trips per article, not per feed, were the real cost. Rewrote to collect all of a feed's rows and issue one multi-row `INSERT ... ON CONFLICT DO NOTHING` per feed. Verified locally against the dev DB first that `ON CONFLICT` still dedupes correctly *within* a single multi-row statement, not just across separate ones. Also bumped the shared pg Pool's `max` (10 → 20) to match the fetch concurrency.
  4. Even after that fix, a job still showed `Running` in `kubectl get job` for 4+ minutes despite its own log output already showing `Done: 282/326 feeds ok...` — the actual root cause: `poll-once.js` awaited `pool.end()` after logging completion, and a client left in a bad state by any earlier query could make that hang indefinitely with nothing left to do, until the deadline killed the stuck pod. Since this is a one-shot job pod that gets torn down the instant the process exits anyway, replaced the graceful-drain wait with a direct `process.exit(0)`. **This was the actual fix** — the very next run completed cleanly in 21s (284/326 feeds ok, 34 new articles).
  - Also bumped `activeDeadlineSeconds` 240s → 280s as a safety margin regardless.
- **Lesson worth keeping**: when a deploy needs a fix, verify each fix actually resolves the observed symptom by re-running the same real test, rather than assuming a plausible-sounding change worked — two of these four fixes were genuinely necessary improvements, but did not by themselves solve the reported failure.
- **Verification**: confirmed all 44 new ISO codes live in the public `/api/countries` response, spot-checked real German-language article content via `/api/countries/DE/articles`. `Test-Build.ps1`: 3/3 core checks passed, k8s checks skipped (same PowerShell-process cold-start quirk as prior deployments). Marked **Build #3** Known Good, commit `56dd32f`.
- **Outcome**: Success. 103 countries live (Africa + Europe complete). - **Real bug #1 — missing fetch() timeout**: first manual poll after deploying hit the CronJob deadline again (`FailureTarget` at ~288s) despite Phase 2.3's concurrency-pool and batch-insert fixes already being live. Root-caused directly: `fetchFeed()`'s `fetch(feed.feed_url, { headers })` had no timeout at all — rss-parser's own `timeout` option only bounds the XML-parsing step on text already received, not the network fetch. Asia's more geographically diverse and less reliable feeds (vs. Europe) exposed this: a single hanging TCP connection could occupy a worker-pool slot indefinitely, eventually starving the whole poll even with 20-way concurrency. Fixed with `signal: AbortSignal.timeout(15000)` on the fetch call. Verified: next run completed in 43s (376/437 ok) instead of failing past the deadline.
- **Real bug #2 — malformed date crashing a whole feed's batch insert**: that same verification run surfaced a live error — `invalid input syntax for type timestamp with time zone: "0NaN-NaN-NaNTNaN:NaN:NaN.NaN+NaN:NaN"` from Liberté-Algérie (Algeria, from the earlier Africa batch — this bug existed before Phase 2.5 but only got noticed once fetch-level failures stopped masking it). A malformed `isoDate`/`pubDate` string produces a JS `Invalid Date`, which is truthy (not null) and was passed straight through to the batched multi-row `INSERT`, failing every article in that feed's batch over one bad item. Fixed by detecting `isNaN(date.getTime())` and falling back to `null` (the column is nullable) instead of letting one malformed item take down the whole feed's poll. Verified locally that `new Date('not-a-date')` correctly triggers the `isNaN` branch before deploying. Re-ran the verification poll a third time: 379/437 ok, 37s, zero date errors.
- **Lesson reinforced**: this is now the second deployment in a row where the worker's scale-driven failures took multiple iterations to actually root-cause, and in both cases the fix that "sounded right" wasn't the one that actually worked until re-verified against a real re-run. Continuing to treat "I fixed it" as a hypothesis to test, not a conclusion, paid off again.

## 2026-07-26 23:25 - 2026-07-27 08:25 — Automated off-cluster Postgres backups (HIGH risk, maintenance window)

- **Type**: HIGH risk per `Get-ChangeRisk.ps1` (new database/infrastructure). Proposed a maintenance window (~30-45 min, no downtime expected) with a concrete design; user approved "yes, proceed now" with the instance-principal (no static credential) option.
- **Design**: daily CronJob (03:00 UTC) runs `pg_dump | gzip`, uploads to a **new dedicated** OCI Object Storage bucket `nouvellesdupays-db-backups` (uk-london-1) — deliberately separate from Tekeche's `tekeche-velero-backups` bucket so a problem in one app's backup path can't touch the other's. Auth via OCI **instance_principal**, reusing the existing `tekeche-oke-nodes-dg` dynamic group (already matches all OKE nodes in the compartment) plus a brand-new IAM policy (`nouvellesdupays-backup-bucket-policy`) scoped to just this one bucket — no new static secret anywhere. 30-day retention via a server-side Object Storage lifecycle rule, not application code.
- **Recovery point**: `2026-07-26_23-25-22_before-automated-off-cluster-postgres-ba` — taken before any infra changes, per protocol, even though the change itself is purely additive (new CronJob, new bucket, new policy — nothing existing gets modified).
- **Real bugs hit and fixed along the way** (four, in sequence — each caught by actually testing, not assumed away):
  1. Object Storage's lifecycle-policy feature failed with `InsufficientServicePermissions` on the first attempt — turns out the `objectstorage-<region>` service principal itself needs an explicit IAM grant (separate from the dynamic-group grant used by the CronJob) before it's allowed to execute scheduled deletions on the bucket's behalf. Added a second policy statement for that.
