## 2026-07-26 16:24-17:36 — Phase 2.3: full European continent expansion + worker scaling fix

- **Type**: Two related changes in one session — additive seed data (MEDIUM risk) followed by a worker code fix discovered while verifying the deployment.
- **Scope**: All 44 remaining European countries (Western, Southern, Northern, Eastern Europe, the Balkans, and Russia), at the user's request to "move on to another continent" after Africa. 129 new publishers, individually curl-verified. Countries: 59 → 103.
- **Thin coverage, documented honestly**: Luxembourg (1 feed), Ukraine (2 — most outlets Cloudflare-blocked), Belarus (1 — only the state news agency BELTA worked, all independent outlets blocked), Montenegro (2).
- **Recovery point**: `2026-07-26_16-28-49_before-add-44-european-countries-and-the` (full DB dump, 3.7MB) — first attempt was PARTIAL (no Bastion tunnel active), re-ran after establishing one for a complete snapshot before deploying.
- **Real bug found and fixed, in three iterations**: after seeding + deploying, a manual worker poll job hit the CronJob's `activeDeadlineSeconds` (240s) and got killed before finishing — feed count had grown from 48 (Phase 2 Stage 1) to 326 (post-Europe), a ~7x increase the original sequential one-feed-at-a-time polling design never accounted for.
  1. First fix attempt: chunked feeds into lockstep batches of 20 via `Promise.all` per chunk. **Still failed** — a lockstep batch pays its slowest straggler's full cost (up to the 15s per-feed timeout) on *every* chunk, so 17 chunks × up to 15s ≈ still blew the deadline. Verified this directly rather than assuming the first fix worked.
  2. Second fix: replaced with a real worker-pool pattern (fixed number of workers pulling the next feed off a shared queue as it finishes, not barrier-synchronized batches). **Still failed**, and only marginally faster — pointed at a different bottleneck.
  3. Found the actual bottleneck: `pollFeed` awaited one `INSERT` per article, and several European feeds (La Repubblica, Lenta.ru, Vísir, etc.) carry 50-200+ items each — serialized round trips per article, not per feed, were the real cost. Rewrote to collect all of a feed's rows and issue one multi-row `INSERT ... ON CONFLICT DO NOTHING` per feed. Verified locally against the dev DB first that `ON CONFLICT` still dedupes correctly *within* a single multi-row statement, not just across separate ones. Also bumped the shared pg Pool's `max` (10 → 20) to match the fetch concurrency.
  4. Even after that fix, a job still showed `Running` in `kubectl get job` for 4+ minutes despite its own log output already showing `Done: 282/326 feeds ok...` — the actual root cause: `poll-once.js` awaited `pool.end()` after logging completion, and a client left in a bad state by any earlier query could make that hang indefinitely with nothing left to do, until the deadline killed the stuck pod. Since this is a one-shot job pod that gets torn down the instant the process exits anyway, replaced the graceful-drain wait with a direct `process.exit(0)`. **This was the actual fix** — the very next run completed cleanly in 21s (284/326 feeds ok, 34 new articles).
  - Also bumped `activeDeadlineSeconds` 240s → 280s as a safety margin regardless.
- **Lesson worth keeping**: when a deploy needs a fix, verify each fix actually resolves the observed symptom by re-running the same real test, rather than assuming a plausible-sounding change worked — two of these four fixes were genuinely necessary improvements, but did not by themselves solve the reported failure.
- **Verification**: confirmed all 44 new ISO codes live in the public `/api/countries` response, spot-checked real German-language article content via `/api/countries/DE/articles`. `Test-Build.ps1`: 3/3 core checks passed, k8s checks skipped (same PowerShell-process cold-start quirk as prior deployments). Marked **Build #3** Known Good, commit `56dd32f`.
- **Outcome**: Success. 103 countries live (Africa + Europe complete). The worker-scaling fix is durable infrastructure — it should hold for further continental expansions without needing to revisit the CronJob deadline again, since the bottleneck (hanging pool drain) is now structurally gone rather than papered over with a bigger timeout.

- **Type**: Additive seed data (MEDIUM risk) followed by two more real worker fixes, discovered the same way as Phase 2.3 — by actually re-running the verification poll after each fix rather than assuming it worked.
- **Scope**: All 47 Asian countries across East Asia, Southeast Asia, South Asia, Central Asia, the Middle East, and the Caucasus. 165 new publishers, individually curl-verified. Countries: 103 → 150. Feed count: 326 → 437.

- **Recovery point**: `2026-07-26_19-14-12_before-add-47-asian-countries-and-their` (full DB dump, 9.5MB).
- **Real bug #1 — missing fetch() timeout**: first manual poll after deploying hit the CronJob deadline again (`FailureTarget` at ~288s) despite Phase 2.3's concurrency-pool and batch-insert fixes already being live. Root-caused directly: `fetchFeed()`'s `fetch(feed.feed_url, { headers })` had no timeout at all — rss-parser's own `timeout` option only bounds the XML-parsing step on text already received, not the network fetch. Asia's more geographically diverse and less reliable feeds (vs. Europe) exposed this: a single hanging TCP connection could occupy a worker-pool slot indefinitely, eventually starving the whole poll even with 20-way concurrency. Fixed with `signal: AbortSignal.timeout(15000)` on the fetch call. Verified: next run completed in 43s (376/437 ok) instead of failing past the deadline.
- **Real bug #2 — malformed date crashing a whole feed's batch insert**: that same verification run surfaced a live error — `invalid input syntax for type timestamp with time zone: "0NaN-NaN-NaNTNaN:NaN:NaN.NaN+NaN:NaN"` from Liberté-Algérie (Algeria, from the earlier Africa batch — this bug existed before Phase 2.5 but only got noticed once fetch-level failures stopped masking it). A malformed `isoDate`/`pubDate` string produces a JS `Invalid Date`, which is truthy (not null) and was passed straight through to the batched multi-row `INSERT`, failing every article in that feed's batch over one bad item. Fixed by detecting `isNaN(date.getTime())` and falling back to `null` (the column is nullable) instead of letting one malformed item take down the whole feed's poll. Verified locally that `new Date('not-a-date')` correctly triggers the `isNaN` branch before deploying. Re-ran the verification poll a third time: 379/437 ok, 37s, zero date errors.
- **Lesson reinforced**: this is now the second deployment in a row where the worker's scale-driven failures took multiple iterations to actually root-cause, and in both cases the fix that "sounded right" wasn't the one that actually worked until re-verified against a real re-run. Continuing to treat "I fixed it" as a hypothesis to test, not a conclusion, paid off again.
- **Verification**: all 47 new ISO codes confirmed live in `/api/countries`, spot-checked real article content for South Korea (Yonhap) — Saudi Arabia's two feeds happened to fail on this particular poll cycle (Arab News 403, Saudi Gazette malformed XML) which is normal feed-level flakiness, not a code issue, matching the ~13-14% miss rate seen across every continent so far. `Test-Build.ps1`: 3/3 core checks passed. Marked **Build #4** Known Good, commit `334e08c`.

- **CORS fix**: was `cors, { origin: true }` — reflected any requesting Origin, effectively open to every website. Replaced with an explicit allowlist (`nouvellesdupays.com`, `www.nouvellesdupays.com`, `localhost:3000` for local dev). Requests with no Origin header (curl, server-to-server, health checks) still pass through untouched — CORS only governs browser fetches. **Caught a real bug in my own first draft before deploying**: the initial version rejected disallowed origins via `cb(new Error(...), false)`, which turns every disallowed-origin request into a 500 — wrong status code, and would have broken any non-browser caller that happens to set an Origin header. Verified locally: 100 requests succeed, the 101st in the same window returns 429.
- **Real Velero finding along the way**: while investigating the backups task, discovered the cluster's existing Velero installation (used for `tekeche-daily`) has **no VolumeSnapshotClass and no node-agent (restic/kopia) daemonset** — meaning Velero here only backs up Kubernetes object manifests, not actual PVC data. A naive "just add a Velero schedule for nouvellesdupays" fix would have given false confidence: Postgres's actual data would never have been captured. This changes the backup approach (see next entry, once implemented) to a logical `pg_dump`-based backup pushed to object storage rather than relying on Velero for the database.

## 2026-07-26 23:25 - 2026-07-27 08:25 — Automated off-cluster Postgres backups (HIGH risk, maintenance window)

- **Type**: HIGH risk per `Get-ChangeRisk.ps1` (new database/infrastructure). Proposed a maintenance window (~30-45 min, no downtime expected) with a concrete design; user approved "yes, proceed now" with the instance-principal (no static credential) option.

- **Recovery point**: `2026-07-26_23-25-22_before-automated-off-cluster-postgres-ba` — taken before any infra changes, per protocol, even though the change itself is purely additive (new CronJob, new bucket, new policy — nothing existing gets modified).
- **Real bugs hit and fixed along the way** (four, in sequence — each caught by actually testing, not assumed away):
  1. Object Storage's lifecycle-policy feature failed with `InsufficientServicePermissions` on the first attempt — turns out the `objectstorage-<region>` service principal itself needs an explicit IAM grant (separate from the dynamic-group grant used by the CronJob) before it's allowed to execute scheduled deletions on the bucket's behalf. Added a second policy statement for that.
  2. First Kaniko build of the new backup image failed on push: `DENIED... not authorized` — pushing to a brand-new OCIR repository name needs different permissions than pushing to an already-existing one (the api/worker/web repos already existed from earlier builds, so this was the first time a new repo name was involved). Fixed by pre-creating the `nouvellesdupays-backup` repo directly via an admin-level `oci artifacts container repository create` call before retrying the build.
  3. Second build attempt failed on `COPY backup.sh /backup.sh` — Kaniko's build context is the whole repo root (same as api/worker), not the Dockerfile's own directory; needed `COPY apps/backup/backup.sh /backup.sh`. Same convention the other Dockerfiles already use, missed it on the first pass for this new one.
  4. No `.gitattributes` existed anywhere in this repo, meaning `.sh`/Dockerfile line endings weren't protected from Windows' CRLF conversion — added one forcing LF for `*.sh` and `Dockerfile`, since a CRLF shebang line would have silently broken the backup script inside its Linux container with zero test coverage to ever catch it.

Restored cleanly, zero errors, and row counts matched production exactly: **190 countries, 514 publishers, 19,602 articles**. This is also the realistic disaster-recovery procedure, not just a synthetic local check.

## 2026-07-27 14:30-15:48 — Fix port-80 HTTP (HIGH risk, maintenance window, TWO real root causes found)

- **Type**: HIGH risk per `Get-ChangeRisk.ps1` (load-balancer infrastructure). Proposed a maintenance window (~15-20 min, no impact to the working HTTPS path since port 80 already had zero working traffic); user approved.
- **Background**: known, previously-unchased gap since the original TLS/deploy work — bare `http://nouvellesdupays.com` hung indefinitely (TCP connect timeout, not even a refused connection), while HTTPS worked fine.
- **Investigation, not guessing**: reproduced first (`curl -v` showed a pure TCP-level hang, no SYN-ACK). Checked the NLB backend-set health directly: `ingress-backends-http` (port 80) was `CRITICAL` for both backends, while `ingress-backends` (port 443) was `OK`. Diffed the two backend sets' full config (same technique as the earlier `is-preserve-source` fix) and found root cause #1: the port-80 health checker used protocol `HTTP` expecting exactly `return-code: 200` on `/`, but the Ingress correctly has `nginx.ingress.kubernetes.io/ssl-redirect: "true"` set, so nginx responds to plain HTTP with a `308` redirect — the health check was destined to fail by design mismatch, unrelated to actual backend health.

This ruled out the backend itself and pointed at something between the NLB and the nodes.
- **Root cause #2, found by comparing NSG rules for the two ports**: the OKE worker nodes' NSG has an explicit `INGRESS` rule allowing TCP port **30443** from `10.0.1.0/24` (the NLB's subnet) — but **no equivalent rule for port 30080 existed at all**. - **Verification, from outside the network (not just in-cluster)**: `curl http://nouvellesdupays.com/` now returns a clean `308` to `https://`; following the redirect lands on a working `200`. Confirmed the same for `www.nouvellesdupays.com` and the `/api` path. `Test-Build.ps1` 3/3.
- **No code/image changes** — pure OCI infrastructure fix (NLB backend-set health checker + NSG rule). Marked **Build #12** Known Good anyway (same commit as Build #11, `d5d2e5`6) to keep the verified-healthy timestamp in the record.
